# 历史截图归档（`docs/archive/screenshots/`）

这里的图**不是交付配图**，是开发过程的 before/after 验收证据与旧版整站截图。
当前版本的界面图在 [`docs/screenshots/current/`](../../screenshots/README.md)（正文引用只引用那里）。

## 1. 为什么是「归档」而不是「删除」

- 每张图都对应一次具体的界面回归：图的文件名、目录名和（部分目录里的）`README.md` 记着
  **基线版本、改动提交、关键量测与复现命令**，删掉就失去「当时为什么这样改」的证据；
- 体检清单 P2-2 的要求是「按当前版本 UI 与历史对比分目录」「关键截图在正文有引用」，
  并没有要求删除历史对比图，因此按**保留 + 移出主视觉目录**处理；
- 仓库体积已经受控：这批图合计 13.24 MB / 161 张 PNG，最大的 `history/` 有 119 张（10.12 MB）。

## 3. `history/` 的命名规律

两批内容混在一起，按文件名区分：

1. **整站首拍**（`01-login.png` … `17-about-update.png`）：早期版本用
   `scripts/dev-only/legacy/frontend-ui_check.mjs` 那类脚本一次拍完七个页面与首次引导流程，
   文件名是「序号-页面」。
2. **逐轮对比**（`18-…` 起）：`<序号>-<主题>-before.png` / `-after.png`，
   序号越大越新；主题覆盖会话历史、抽屉、移动端、文档失败态、Wiki 目录、模型分组、
   小字清理、关于页版本号等。**同序号可能是不同主题**（例如 `23-` 有 chat-switch 与
   documents-failure 两组），按完整文件名看。

这些图当时由一次性脚本拍摄、人工判读，**没有断言、没有退出码约定，不属于测试**。

## 4. 怎么引用历史对比

正文（论文/设计说明）只引用当前版本图。若某处确实要说明「改前 vs 改后」，
在 `docs/*.md` 里用相对路径引用，例如：

```markdown
![改前：整页被长会话撑高](archive/screenshots/chat-scroll-rounded/before.png)
```

并确保：
- 说明里写清基线版本与改动提交（各目录 README 里有）；
- 同一处不要既贴历史图又贴当前版本图，读者会分不清哪个是现在的界面。

## 5. 后续怎么处理

- **不再往里加新图**：新的一次性对比图放 `docs/screenshots/`（当前版）或直接放 PR 描述里；
  确实需要长期保留的对比证据，再进本目录并补一行说明到本文 §2。
- 若将来决定**真正删除**其中某个目录以压缩仓库体积，属于删除类操作，需要维护者明确同意；
  在此之前它们保持只读归档状态。
