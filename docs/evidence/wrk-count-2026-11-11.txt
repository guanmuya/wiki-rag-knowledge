# 文档口径收尾：`WRK_*` 条数核准 + 旧数字扫查（2026-11-11）

对应 todo「文档口径收尾：核准 WRK_* 数量并清理过时数字」。

**起因**：仓库治理那轮报告说 `docs/FACTS.md` 写 `config.py` 有 41 个 `WRK_*`，而它在同一个文件里
数到 43 个；且 FACTS 自己的算式「旧写 38 + 新增 4 个 `WRK_LOGIN_*` + `WRK_HARDEN_SECRETS`」
= 43，与 41 对不上。

**结论**：**43**。41 是批次三的算式笔误（同一段写的是「38 + 5」）。本轮只改文档：
`docs/FACTS.md` 按代码订正为 43 并补了可复现的数法（§1.3），其余文档保持「只指向、不复述」。
本文件是这次核准与扫查的原始证据。

## 2. 核准命令与输出（可复现）

### 2.1 主命令：数 `config.py` 里 `WRK_*` 的唯一名字

仓库根目录执行，一条命令、无第三方依赖：

```
python -c "import re,pathlib;print(len(set(re.findall(r'\bWRK_[A-Z0-9_]+\b', pathlib.Path('backend/app/config.py').read_text(encoding='utf-8')))))"
```

输出：

```
43
```

（这条命令在 PowerShell 7 与 bash 下都能原样跑通：外层用双引号、内层字符串用单引号，
两边都按原样传给 Python。PowerShell 里把外层换成单引号反而会失败——原生命令收到的双引号会被吞掉。）

### 2.2 交叉校验：只数真正被 `os.getenv(...)` 读取的名字

实际是怎么跑的（PowerShell 7 的 here-string，把脚本喂给 `python -`；bash 下等价的写法是
`python - <<'PY' … PY`）：

```
@'
import re, pathlib
t = pathlib.Path("backend/app/config.py").read_text(encoding="utf-8")
allt = sorted(set(re.findall(r"\bWRK_[A-Z0-9_]+\b", t)))
env = sorted(set(re.findall(r"os\.getenv\(\s*\"(WRK_[A-Z0-9_]+)\"", t)))
print("config.py WRK_ unique tokens:", len(allt))
print("config.py WRK_ read via os.getenv:", len(env))
print("tokens not passed to os.getenv:", sorted(set(allt) - set(env)))
print("getenv names not in token set:", sorted(set(env) - set(allt)))
print("lines:", len(t.splitlines()))
'@ | python -
```

实际输出：

```
config.py WRK_ unique tokens: 43
config.py WRK_ read via os.getenv: 43
tokens not passed to os.getenv: []
getenv names not in token set: []
lines: 132
```

两条口径同为 **43**，且两个集合完全重合：43 个名字**全部**真的被 `os.getenv` 读取，
没有「只在注释里出现」的幽灵项（唯一的注释提及是 `WRK_HARDEN_SECRETS`，它本身就是一项）。
`WRK_LOCK_RETRY` 是 `WRK_LOCK_RETRY_ATTEMPTS` 的兼容别名，出现在同一处 `os.getenv` 的外层与内层
（`config.py` 的 `LOCK_RETRY_ATTEMPTS`），按「一个环境变量名算一项」计入。

## 3. 与旧口径 41 的差异

| 口径 | 值 | 来历 |
| --- | --- | --- |
| FACTS 最初写的 | 38 | 体检当时（P0 批次）的读数：`docs/HEALTH_CHECK.md` §3.2 D6「`config.py` 出现 38 个 `WRK_*`」 |
| P1-8（批次三）新增 | +5 | 4 个 `WRK_LOGIN_*`（`MAX_FAILURES` / `MAX_FAILURES_PER_SOURCE` / `FAIL_WINDOW` / `LOCK_SECONDS`）+ `WRK_HARDEN_SECRETS` |
| P1-8 落进 FACTS 的数 | 41 | **算错**：`38 + 5 = 43`，不是 41；同一段的算式与实际数字自相矛盾 |
| 本轮按代码重数 | **43** | 本文件 §2 的两条口径一致 |

38 与 43 相差的 5 个，正是 P1-8 新增的 5 个；也就是说 41 既不是「38 + 4」（漏了
`WRK_HARDEN_SECRETS`）也不是「38 + 5」，没有任何代码树算得出 41——它是纯粹的笔误。

### 4.3 结论

- 除 `docs/FACTS.md` 自身与上表的「历史语境」外，仓库里**不再有**把 `583` / `638` / `673`
  当作当前基线的表述，也没有 `21 张表` / `38 个 WRK_` / `41 个 WRK_` 的现行口径。
- 六份文档（`README.md`、`DESIGN.md`、`EXPERIMENT.md`、`THESIS.md`、`HANDOFF.md`、`API.md`）
  对版本、表数、并发、锁超时、测试基线一律只放链接；`CHANGELOG.md`、`CONTRIBUTING.md`
  同样只写指向（本轮复核为真）。
- 现行表数口径统一为 **23 张表**（`models.py` 的 22 个 `__tablename__` + `migrations.py` 的
  `schema_migrations`）：`README.md` 目录树、`docs/THESIS.md` §2.1/§2.2、`docs/API.md` §8.2 都是 23，
  无残留的 21 或 19（后两者只出现在 FACTS 的历史追溯段落与 `HEALTH_CHECK.md` 快照里）。
