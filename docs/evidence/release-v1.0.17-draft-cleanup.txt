以及两处与任务描述不一致、需要留档的事实：草稿并非「0 资产」，以及「空草稿」这个结论当初是怎么来的。

## 2. 删除前核对（身份三项 + 资产）

命令与实测（`gh` 已登录；本文件不记录任何令牌值）：

```
gh release view v1.0.17 --repo guanmuya/wiki-rag-knowledge \
  --json tagName,name,isDraft,publishedAt,createdAt,url,assets
```

| 检查项 | 实测结果 | 与任务描述是否一致 |
| --- | --- | --- |
| 是不是 v1.0.17 那条 | `tagName = v1.0.17`，`name = v1.0.17 问答与 Wiki 体验改进` | 一致 |
| 状态是不是草稿 | `isDraft = true`，`publishedAt = null` | 一致 |
| 资产数是不是 0 | **`assets.count = 2`**：<br>`wiki-rag-knowledge-1.0.17-x64-setup.exe.blockmap` 138,074 B（uploaded）<br>`latest.yml` 376 B（uploaded） | **不一致** |
| 创建时间 | `2026-11-07T13:45:27Z` | 一致（2026-11-07 的遗留） |
| Release URL | `https://github.com/guanmuya/wiki-rag-knowledge/releases/tag/untagged-b7914fff4f77d68f65bf` | 草稿未绑 tag，故为 `untagged-*` |

「空草稿」这个说法当时是**推断**而不是实测：v1.0.18 发布时用的是
`GET /releases/tags/v1.0.17`，该端点在对象是草稿时**恒返回 404**，
于是把 404 读成了「不存在 / 无资产」。用 `gh release view`（对草稿可见）才看到真实资产数。

草稿里的 `latest.yml` 内容（376 B，用 `gh api .../releases/assets/<id> -H "Accept: application/octet-stream"` 读取）：

```
version: 1.0.17
files:
  - url: wiki-rag-knowledge-1.0.17-x64-setup.exe
    sha512: QOGsGpxHMa91zbIpf/ik61SV+rH34DtbHq+fmlG9oZsKVd5MBXJRHrvvkVX5XXxqvgNt8SD/tfXQaliZXiVdEA==
    size: 131918244
path: wiki-rag-knowledge-1.0.17-x64-setup.exe
releaseDate: '2026-11-07T13:08:54.218Z'
```

即 `latest.yml` 指向的 131,918,244 B 安装包**从未上传成功**，
这份草稿是 2026-11-07 那次发布中断后留下的半成品（元数据 + 差分块，缺主包）。

删除前对外影响面（匿名、不带令牌）：

```
GET https://api.github.com/repos/guanmuya/wiki-rag-knowledge/releases?per_page=100
→ 19 条，不含 v1.0.17                        （草稿不计入公开列表）

HEAD https://github.com/guanmuya/wiki-rag-knowledge/releases/download/untagged-b7914fff4f77d68f65bf/latest.yml
→ 404                                        （草稿资产匿名不可下载）
```

结论：这条草稿对外不可见、资产拿不到，删它不影响任何用户的更新；
但「资产数为 0」这一条与实测不符，因此按任务约定先停下询问，用户确认后才执行删除。

## 3. 删除命令与输出

```
> gh release delete v1.0.17 --repo guanmuya/wiki-rag-knowledge --yes --cleanup-tag=false

（无输出）
> exit code: 0
```

`--cleanup-tag=false` 是显式写出来的：`gh` 的 `--cleanup-tag` 默认就是 false，
写死它是为了表明「只删 Release、不删 tag」是本次的明确要求，而不是默认行为碰巧如此。
