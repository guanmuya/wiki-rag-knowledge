## 4. 创建 tag 与上传

### 4.1 tag

用**平台的 tag 能力**在 `cda67b2` 上创建 `v1.0.19`（不是 `git tag` + `git push`，
也不是 `electron-builder --publish always`），随后核对指向：

```
$ git ls-remote --tags origin | Select-String 'v1\.0\.19'
cda67b297af913ceadcb6a25f78fdd82668cfa2b	refs/tags/v1.0.19

$ gh api repos/guanmuya/wiki-rag-knowledge/git/ref/tags/v1.0.19
{"ref":"refs/tags/v1.0.19","object":{"sha":"cda67b297af913ceadcb6a25f78fdd82668cfa2b","type":"commit"}}
```

> **与任务约定的差异（如实记录）**：约定写的是「annotated tag，说明写 v1.0.19 的要点」，
> 但平台 tag 能力只接受 `tag` + `target` 两个参数、没有说明字段，产出的是
> **轻量 tag**（`object.type=commit`，与 `v1.0.18` 那次相同）。
> 没有为了加说明去绕过平台改用 `git push` 推 tag（工作区无远端凭据，且约定禁止绕过）。
> 版本要点写在 Release 正文里，tag 本身不带说明。

### 4.2 上传

| 项 | 值 |
| --- | --- |
| 账号 | `gh auth status` → `Logged in to github.com account guanmuya`（本机 keyring，即仓库属主） |
| 令牌处理 | **未读取、未复制、未落盘任何令牌值**；`$env:GH_TOKEN` / `$env:GITHUB_TOKEN` 均不存在，靠 `gh` 自身登录态执行 |
| 命令 | `gh release create v1.0.19 --verify-tag --title "v1.0.19" --notes-file <正文> latest.yml <安装包> <blockmap>` |
| 结果 | 退出码 0，输出 `https://github.com/guanmuya/wiki-rag-knowledge/releases/tag/v1.0.19` |

用 `--verify-tag` 而不是 `electron-builder --publish always`：前者在 tag 缺失时直接失败，
后者在 Release 不存在时会自己建 Release 并**把 tag 打到当前分支 HEAD**。

Release 正文取自 `docs/RELEASE_NOTES_v1.0.19.md` **§1「Release 正文草稿（可直接粘贴）」**，
不是整份文件——§2 的内部上传命令与 §3「本版没做的事」不适合对外（与 v1.0.18 一致的做法）；
发布前后逐字比对过，正文与 §1 代码块内容完全相同（1,011 字符）。

### 校验 3：`latest.yml` 与实际上传的安装包逐项一致

1. **版本与文件名**：`version: 1.0.19`、`path` 与 `files[0].url` 都是
   `wiki-rag-knowledge-1.0.19-x64-setup.exe`，与上传的资产名逐字一致。
2. **sha512 / size**：`latest.yml` 里的 `sha512`、`size` 与本地重算值完全相同
   （`node:crypto` 与 `Get-FileHash -Algorithm SHA512` 两条路算出的 hex 一致，
   再转 base64 与 `latest.yml` 相同；字节数 `131534818` 相同）。
3. **服务端 digest 兜底**：GitHub 对上传资产计算的 `digest` 与本地 SHA-256 逐一相同
   （见校验 1 的三行），说明**上传到服务器的字节就是本地这三个文件**，排除上传截断/损坏。
4. **远端 `latest.yml` 与本地逐字相同**：匿名下载下来算 SHA-256 =
   `56e35f33…`，与本地一致。
