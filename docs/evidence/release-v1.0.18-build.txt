### 3.1 第二次实跑的两条失败：`test_agent_runtime.py` 的 15 秒等待撞上本机慢 DNS

失败的是 `test_kb_session_flow` 与 `test_switch_core_mid_session`，报错都是同一个 `_wait_run()` 超时：

```
AssertionError: run 6 未在 15.0s 内结束：{'status': 'running', ... 'text': '正在检索 1 个知识库…'}
```

判定为**本机网络环境导致的已知偶发，与本轮改动无关**，三条证据：

1. **把本轮改动全部 `git stash -u` 掉、回到 `master` `f1fdecd` 原样**，单跑该文件同样是
   `1 failed, 12 passed`（失败项相同）。本轮只改版本号与文档，不可能影响 Agent 运行时。
2. **本机解析测试里那个假域名很慢**：`Resolve-DnsName example.test` 实测 **11.45s / 11.09s / 11.07s**，
   请求 `https://example.test` 耗时 **10.59s**；而 `_wait_run()` 只等 **15s**
   （`backend/tests/test_agent_runtime.py:28`）。`_make_model()` 的 `base_url` 正是
   `https://example.test`，一次失败的出网调用就把 15 秒预算吃掉。单独复跑该文件 5 次，
   `test_switch_core_mid_session` **5/5 失败**（本机网络决定）；`test_kb_session_flow` 单跑 5/5 通过，
   只在全量跑的负载下偶发。
3. **CI 是权威运行**（`docs/FACTS.md` §2.4）：`master` `f1fdecd` 的 CI run `42953906893`
   是 **completed / success**，同一套后端用例在 GitHub runner 上（对 `.test` 直接 NXDOMAIN）全绿。
   这件事与 `docs/FACTS.md` §2.5 记的「`_wait_run()` 只等 15 秒、负载高时偶发」是同一个已知问题。

> 处置：本轮**不改测试、不改业务代码**去「修绿」（发布任务边界就是不碰逻辑）；
> 「让这两条用例不依赖真实 DNS」已另记待办。发版判断以 CI 为准，本机这次的 705/2
> 如实留在这里，不写成「全绿」。

## 6. 发布凭据探测结果（如实记录）

| 探测 | 结果 |
| --- | --- |
| `$env:GH_TOKEN` | **不存在** |
| `$env:GITHUB_TOKEN` | **不存在** |
| `gh auth status` | 显示本机装有 GitHub CLI 且已登录 `guanmuya`（keyring 存储，作用域 `gist, read:org, repo, workflow`）——这是操作者本机的登录态，**未在本轮取用**，也**没有**把任何 token 写入文件、日志或聊天 |

结论：**本轮不上传**。原因有两条，缺一不可：

1. **`v1.0.18` tag 还不存在，也不该由本轮创建**。tag 要打在 `master` 的合并提交上（平台在合并后创建）；
   而 GitHub Release 必须挂在某个 tag 上——`electron-builder --publish always` 在 release 不存在时
   会自己建 release 并**连带创建 tag**，那会把 `v1.0.18` 指到错误提交。所以本轮只构建、不发布。
2. 上传是「外部权威动作」，按团队约定需由用户在发布时点确认，并可现取本机 `gh` 登录态执行
   （`gh auth token` 即可，命令见 `docs/RELEASE_NOTES_v1.0.18.md` §2）。

## 7. 合并落地后要做什么（命令已写好，照抄即可）

完整步骤与校验在 [`docs/RELEASE_NOTES_v1.0.18.md`](../RELEASE_NOTES_v1.0.18.md) §2，摘要：

```powershell
# 0) 先确认 tag 已在远端（由平台在合并后创建）
git ls-remote --tags origin | Select-String 'v1\.0\.18'

# 1) 建 Release 并上传三个资产；--verify-tag 保证 tag 不存在时直接失败，不会顺手建 tag
gh release create v1.0.18 --verify-tag --title "v1.0.18" --notes-file docs/RELEASE_NOTES_v1.0.18.md `
  frontend/release/updates/latest.yml `
  frontend/release/updates/wiki-rag-knowledge-1.0.18-x64-setup.exe `
  frontend/release/updates/wiki-rag-knowledge-1.0.18-x64-setup.exe.blockmap

# 2) 匿名可下载性（三个都应为 200；刚上传后 1–2 分钟 CDN 延迟属正常）
$base = 'https://github.com/guanmuya/wiki-rag-knowledge/releases/download/v1.0.18'
foreach ($f in @('latest.yml','wiki-rag-knowledge-1.0.18-x64-setup.exe','wiki-rag-knowledge-1.0.18-x64-setup.exe.blockmap')) {
  "$f -> $(curl.exe -sIL -o NUL -w '%{http_code}' "$base/$f")"
}
```

> 换机器重建：`cd frontend && node scripts/build.mjs`。前提是 Node 22+ 与 pnpm、能联网下载
> Electron 二进制与 NSIS 工具链，以及一个装了 `backend/requirements-build.txt` 的 Python 环境
> （默认取仓库根 `.venv`，可用 `WRK_PYTHON` 覆盖）。构建**不会**改变 `latest.yml` 之外的任何仓库文件。
