# Windows 桌面版 CI/CD 与自动发布设计

- 日期：2026-11-16
- 仓库：`guanmuya/wiki-rag-knowledge`
- 设计基线：`master` 的 `106c515`；实施前应重新核对默认分支最新状态。

## 目标和约定

保留当前 PR / `master` 的自动测试。维护者将正式版本标签（例如 `v1.0.23`）推送到 GitHub 后，工作流对该标签指向的代码重新测试；测试、版本检查、构建、安装包验证和发布资产校验全部通过后，自动发布正式 GitHub Release。中间可以使用 Release 草稿存放待校验资产，但整个成功路径不需要人工点击发布。

普通 PR、普通 `master` 提交和手动触发只运行 CI，不自动发布。发版前仍由维护者按版本管理流程更新并合并版本号、发布说明，然后创建并推送标签；这里的“全自动”指标签推送后的检查、打包和正式发布，不包括自动决定版本号或自动创建标签。标签应由维护者的 Git 操作或获授权的独立身份推送：由其他工作流使用默认 `GITHUB_TOKEN` 推送的标签通常不会触发新的 `push` 工作流。

应用已配置从 GitHub Releases 自动更新，正式发布可能使已安装客户端检查并下载新版本。现有配置未提供代码签名证书；下载校验和只能检查文件一致性，不能替代对发布者的签名验证。代码签名列为后续改进，不作为本方案的新增凭据前提。

## 现状和方案选择

- 现有 `.github/workflows/ci.yml` 在 PR 和 `master` 提交上，以 `windows-latest` 运行后端 pytest、前后端契约检查、前端类型检查、Web 构建和前端自动化测试。
- `frontend/scripts/build.mjs` 调用前端构建、PyInstaller 和 electron-builder；`frontend/scripts/build-backend.mjs` 已验证后端可启动并响应健康检查。构建脚本收集更新文件失败时可能只告警，因此发布流程必须另行验证资产。
- 当前前端浏览器测试使用模拟后端；已有的部分 `verify-*` 脚本属于人工验收辅助，不能直接假设它们是可靠的自动化门禁。
- `frontend/electron/update-config.json` 使用该仓库的 GitHub Releases，允许自动下载并在应用退出时安装；当前不接受预发布版本或降级。
- 方案 A：扩展现有 `ci.yml`，在同一个 workflow 内使用 `needs` 串联 CI、打包、验证和发布。**采用方案 A**：依赖关系清楚，测试与构建针对同一个标签提交。
- 方案 B：独立的 `ci.yml` 和 `release.yml`，通过可复用工作流或其他方式复用同一提交的检查结果。适合后续扩大维护规模，但要额外处理跨工作流提交和状态的关联；当前不采用。

## 触发和权限

1. 保留 `pull_request` 指向 `master`、`push` 到 `master`、`workflow_dispatch` 三种现有触发方式；增加推送 `v*` 标签触发。
2. PR 和 `master` 推送运行 CI；版本标签也运行完整 CI，所有后续发布任务依赖本次标签运行的 CI 成功。手动触发只用于验证 CI，不发布。
3. 只有 `push` 标签事件且标签符合严格的正式三段版本格式 `vMAJOR.MINOR.PATCH` 才能发版。其他 `v*` 标签不得创建或修改正式 Release。
4. 标签解析后的提交必须是当前远端 `master` 的祖先提交。抓取足够的 Git 历史后检查，不能只依据标签名判断分支；如果在检查时 `master` 已前进，已合并的标签提交仍可发布。
5. CI / 构建任务仅需仓库读取权限；仅发布任务授予 `contents: write`，使用 GitHub 自动提供的 `GITHUB_TOKEN`。PR 不获得发布凭据，任何外部 PR 内容都不得以发布权限执行。
6. 建议在 GitHub 设置中为 `master` 启用“通过 PR 合并”和“CI 状态检查通过”，并限制正式版本标签的创建、更新和删除。仓库设置是独立操作，实施前需确认当前规则和权限；它们不能代替标签运行中的完整 CI。
7. PR 和普通分支可以取消同一引用上的旧 CI；标签发布运行不得因新提交被取消。正式发布任务按仓库串行，使用支持排队的并发设置；进入发布队列后再次比较现有正式版本，防止较旧版本晚完成并取代较新版本。

## 工作流任务

### 1. `ci`：保留并运行现有检查

继续使用现有 Python、Node.js、pnpm、依赖锁文件和五项命令：

```text
python -m pytest backend/tests -q
pnpm check:contract
pnpm typecheck
pnpm build:web
pnpm test
```

前端命令在 `frontend/` 中执行；浏览器测试继续安装 Playwright Chromium。沿用或完善现有缓存和 pytest 输出 artifact，不引入真实模型服务、真实用户知识库或 API 密钥。CI 状态名称应稳定，以便配置为 PR 必需检查。

### 2. `check-version`：校验发布对象

只对正式版本标签执行，失败即阻断后续发布：

- 标签（去掉 `v`）、`frontend/package.json` 和 `backend/app/main.py` 的版本一致。
- 标签指向的提交属于 `master` 历史，且从该提交检出的代码正是本次测试代码。
- 使用严格版本比较，正式版本必须大于当前已发布的最高正式版本；排除草稿和预发布版本。相同标签对应的已发布 Release 不允许被覆盖。
- 延续现有 `docs/RELEASE_NOTES_v<version>.md` 约定：必须存在与版本对应的说明文件，且能从其第 1 节提取唯一的 `markdown` 围栏代码块作为面向用户的 Release 正文；缺失、为空或存在歧义时停止发布。不得上传包含内部操作步骤的整份说明文件。
- 版本校验不自动修改任何源码或标签。

### 3. `package`：构建并校验本次资产

在新的 Windows runner 上检出同一标签提交，安装锁定的 Python 和前端依赖，创建项目 `.venv`，然后运行 `frontend/scripts/build.mjs` 的非发布模式。此阶段不得使用 `--publish`，以免跳过后续校验直接上传或发布。

将本次构建的以下三个文件作为同一个 Actions artifact 传递给后续任务：

1. `wiki-rag-knowledge-<version>-x64-setup.exe`；
2. `latest.yml`；
3. 与该安装包对应的 `.blockmap`。

即使构建脚本只告警，也必须检查三个文件均存在且非空；安全解析 `latest.yml`，检查版本、文件名、大小和 SHA-512 与安装包一致。不得依赖无声明的传递依赖来解析 YAML；如需解析库，应作为直接开发依赖固定并更新 `pnpm-lock.yaml`。只有通过验证的文件才能上传为后续任务使用的 artifact，建议设定有限的保留时间。

### 4. `smoke-test`：验证实际交付物

沿用构建脚本已有的后端启动和 `/api/health` 检查，并新增可重复、带明确退出状态的 Windows 安装包冒烟测试：在 GitHub 临时环境中安装本次 NSIS 安装包，启动已安装应用，确认 Electron 主窗口和本机后端健康检查可用，然后正常关闭进程。使用临时测试数据和本机回环地址，关闭实际自动更新，不读取用户数据、不调用在线模型。

该步骤需要为项目编写稳定的自动化测试；不把现有人工截图脚本直接视为通过条件。失败或超时即阻断发布，输出足以定位问题的脱敏日志。

### 5. `release`：自动发布正式版本

只有前述任务全成功才执行。下载并再次校验同一份 artifact；在串行发布区再次核对标签指向、版本递增、三个文件和 SHA-512。

先以该现有标签创建 Release 草稿，上传三个文件及第 1 节提取出的发布正文；从 GitHub 以认证方式核对草稿资产的文件名、大小和内容校验值。全部一致后自动将草稿改为正式发布并设为最新正式版，不等待人工审批。任何检查、上传或发布失败都应标记工作流失败，并且不把未验证完整的草稿转成正式版。

重试不能覆盖已发布版本：相同标签已有正式 Release 时，停止并报错，绝不替换资产。已有草稿只有在确认其标签、提交和工作流身份属于同一次发布尝试时才可继续；遇到不属于本次尝试的草稿应停止并提示处理，不能自动删除或覆盖。发布任务必须可重跑并避免把不同版本的安装包与 `latest.yml` 混用。

## 其他自动化的边界

- **CodeQL**：作为独立的安全扫描，覆盖 Python 与 JavaScript/TypeScript，在 PR 和定期任务运行；根据仓库支持情况选择 GitHub 默认设置或独立 workflow。
- **Dependabot**：使用 `.github/dependabot.yml`，按周检查 `/backend` 的 Python、`/frontend` 的 pnpm/npm 和 GitHub Actions；通过 PR 提议更新，由现有 CI 检查，不自动合并或发版。注意 Python 约束文件和 pnpm 锁文件必须保持一致。
- **RAG 离线评测**：可另建定期/手动 workflow，使用演示数据和 `backend/scripts/run_experiments.py` 生成独立报告 artifact；不自动提交结果、不访问真实用户数据，初期不阻塞发版。离线结果不等同在线模型质量。
- 上述安全、依赖和评测属于推荐的后续工作；自动发布主线的实现与测试不依赖它们先完成。不要为了桌面程序虚构服务器部署或数据库备份工作流。

## 验收和失败处理

1. PR 与普通 `master` 提交：运行 CI，不生成正式 Release。
2. 有效正式标签、所有检查通过：只生成一个对应版本的正式 Release，三个文件来自同一构建，可供既有更新器读取，整个发布阶段无人工点击。
3. CI 失败、标签不在 `master` 历史、版本不一致、发布正文缺失或有歧义、资产缺失、哈希错误、冒烟测试失败：工作流失败，不发布正式版本。
4. 预发布或格式错误标签：不发布正式版本；已有正式标签重新运行不得覆盖资产。
5. 下载或上传中断：可识别并安全重试本次草稿，不误改无关草稿或正式版本；并发发版不能让较旧版本成为最新正式版。
6. 首次上线前，用隔离的测试仓库或明确禁用正式发布的验证流程演练，覆盖成功、失败和重复运行；不在正式仓库推送测试标签、创建测试正式 Release 或触碰用户安装的数据。
7. 已发布版本出现问题时，保留诊断记录，修复后发布更高版本；当前客户端禁止降级，不能假定把旧版设为最新就能让已升级用户回退。

发布日志和人工可见报告不得包含 API 密钥、真实知识库文件或用户隐私数据。工作流和设置上线后，应记录触发方法、查看日志的位置以及失败时的处理方式。
